# Joga Placas — Architecture Decision Record (ADR-001)

Status: accepted for implementation on planning/foundation; no production migration authorized.

## Objective

Build one maintainable, secure, extensible platform from the existing repository. Prefer a modular monolith with explicit domain boundaries over microservices or isolated quick fixes. Preserve main and any currently operating system until review and a controlled release are explicitly approved.

## Architectural decisions

### 1. Domain model before database migration

The current Prisma schema is a scaffold, not a production-ready financial model. Do not create or apply an initial migration until the domain design and invariants have been reviewed and validated.

The target model must distinguish these concepts:

- **Purchase/order:** one checkout, receipt, payment method, payer or cashier, total amount, immutable status transitions and idempotency identity.
- **Round participation:** one independent participation in one round. A purchase repeated across 1–10 rounds creates one participation per round while retaining a single upfront checkout/payment. Every participation has its own cutoff eligibility and result lifecycle.
- **Plate selection/allocation:** immutable plate display and normalized key, category-level stake allocations in integer cents, and rule/multiplier snapshots so later configuration changes do not rewrite history.
- **Customer:** a cashier's over-the-counter customer record (name and WhatsApp) must not silently become a player account.
- **Payment:** provider-neutral payment record associated with the checkout, with provider reference, confirmed amount/currency, fees/refunds where available, idempotency, and a verified provider event trail.
- **Wallet ledger:** append-only financial entries with unique idempotency keys. Balance is derived/reconciled from entries; never mutate a balance as an unaudited shortcut. Wallet debit, prize credit, withdrawal reserve/release/payment and refund must be transactionally consistent.
- **Cashier sale and commission:** preserve the cashier as seller, record the commission rate/value snapshot applicable to that sale, and avoid double-counting direct and cashier sales.
- **Withdrawal:** separate requested, reserved, reviewed, processing, paid and rejected states; reviewer is a real user relation; paid requires provider confirmation where Pix payout integration supports it.
- **Round configuration/results and audit:** schedule each recurrence as a concrete round, preserve result/rule snapshots, and audit administrative changes and corrections.

Exact names and relation cardinalities are to be finalized against docs/PRODUCT_SPEC.md before schema implementation. Do not infer missing business rules from implementation convenience.

### 2. Money, time, and transaction safety

- Store money as integer BRL cents; validate non-negative amounts and bounds at domain boundaries.
- Allocate remainders deterministically and test multi-plate and multi-round totals, not only one plate.
- Store instants in UTC; apply America/Sao_Paulo for round scheduling and display.
- Enforce round cutoff on the server and use database transactions/constraints for checkout confirmation, wallet debits, prize credits, withdrawals and webhook processing.
- External callbacks are untrusted until provider authenticity and payment state are verified. Persist webhook event identity and process duplicate deliveries idempotently.
- A UI closing must not imply that a Pix charge was canceled. Only provider-confirmed state changes may settle a payment.

### 3. Application structure

Keep one deployable Next.js/TypeScript application initially, organized by domain: auth, rounds, plates, bets, purchases, payments, wallet, cashiers, admin and audit. Domain rules should be testable without HTTP, UI or provider SDK dependencies. Keep provider integrations behind interfaces/adapters.

Use server-side authorization for every protected operation. The shared login may redirect by role, but role checks must never rely on frontend visibility. Admin credentials are server-secret configured; no public admin signup and no admin secret in client bundles.

### 4. Quality and dependency control

- Keep TypeScript strict and run lint, typecheck, tests, schema validation, client generation and production build in CI.
- Add and commit a package lockfile generated by the package manager; use deterministic CI installs after the lockfile is established.
- Audit direct/transitive dependency vulnerabilities and upgrade deliberately; do not blindly apply major-version changes to a live integration.
- Test business invariants, authorization boundaries, duplicate webhooks, race conditions, ledger reconciliation and round cutoffs.
- Do not treat a successful build or deployment as proof that the user journeys work end to end.

### 5. Environments and release safety

- Keep development, test and production isolated.
- No production payment, production schema migration, destructive data change, or main merge during foundation work.
- Before any migration: review generated SQL, test on a disposable database, prove rollback/recovery, and verify backup/restore strategy.
- Before launch: verify applicable legal/regulatory requirements for the exact game and payment model.

## Implementation gates

**Gate A — Foundation audit:** inspect current repository, workflow, resolved dependencies, deployment state and product requirements; report material risks.

**Gate B — Domain design:** document purchase/participation, customer/cashier, payment, ledger, commission, withdrawal, round and audit relationships. Resolve only genuine business-rule ambiguities with the product owner.

**Gate C — Schema and domain core:** implement the reviewed schema without applying a production migration; validate it and add tests for normalization, allocation, cutoffs and idempotency.

**Gate D — Identity and permissions:** authentication, secure sessions, role/ownership authorization, rate limiting and audit events.

**Gate E — Transaction workflows:** checkout, payment adapter/webhooks, wallet ledger, cashier sale/commission, prizes and withdrawals with concurrency/idempotency tests.

**Gate F — UI and operations:** integrate role-specific interfaces, receipts/history, monitoring, backups, deployment smoke tests and release review.

Each gate must end with concrete evidence (commit, automated checks and a concise risk report). Do not label a gate complete based only on a plan or a successful deploy.
